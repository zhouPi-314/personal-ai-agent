# 云迁移计划（方案 A · 最小云化）

> 状态：已决定方向，尚未开始。目标是在不依赖家里电脑的前提下，让 QQ 聊天 24/7 可用。

## 范围

迁移到阿里云 ECS 的部分：

- QQ 网关（NapCat，Linux）
- PAA 服务（`paa.serve`）
- PostgreSQL（`paa_dev`）
- Web 维护台

保留在本机的部分：

- 任务通道（Harness / dsh）——云上禁用
- 本机 DSH 的免费模型——云端改用官方 API

## 前置条件（全部满足才开始）

1. NapCat 能在 ECS 上登录小号并收发消息（spike 通过）
2. 准备官方模型 API Key，写入云端 `.env`
3. 确认 2 GiB 内存是否够用；不够则先升配到 4 GiB
4. 决定备份目标（云端不再是备份接收方，需要新落点）

## 步骤与估算

| # | 步骤 | 人日 | 通过标准 |
|---|---|---|---|
| 0 | NapCat on Linux spike | 0.5–1 | 小号登录成功，收到并能回复一条消息 |
| 1 | 代码适配 | 1 | 无 Windows 专有路径；配置全部来自环境变量 |
| 2 | 数据迁移 | 0.5 | 恢复后 messages/memories/tasks 计数一致 |
| 3 | 服务化 | 0.5 | systemd 自启、崩溃重拉、日志落盘 |
| 4 | 联调 | 1 | 私聊全链路 + 维护台可访问 |
| 5 | 观察 | 3–7（挂机） | 无掉线、无风控、无内存溢出 |

合计：**3–5 人日 + 观察期**。

## 回滚

- 云端上线后，本机环境**并行保留至少一周**
- 云端故障时把 QQ 网关切回本机（改 NapCat 登录位置即可）
- 数据库双向只保留一个写入方：切换时先停旧端

## 已知风险

| 风险 | 影响 | 应对 |
|---|---|---|
| NapCat 在 Linux 上不可用 | 方案作废 | spike 先行，半天内见分晓 |
| QQ 账号风控 | 服务中断、账号受限 | 小号专用；先在云端低频运行几天 |
| 2 GiB 内存不足 | OOM 杀进程 | 加 swap 或升配 |
| 官方 API 成本 | 持续支出 | 配额熔断已就绪，先设低额度 |
