# 音色与视频理解：三条需求的可行性与边界

> 2026-10-25｜状态：**方案待你确认**，未写实现代码

## 1. 「发一段视频，学里面的音色」

### 技术上要什么

Kokoro 是**固定音色**的模型，不能克隆。要"学某个音色"必须换成带零样本克隆能力的模型：

| 候选 | 体积 | 许可 | 克隆能力 |
|---|---|---|---|
| Qwen3-TTS（0.6B/1.7B） | 2–4GB | Apache-2.0 | ✅ 参考音频克隆 |
| CosyVoice2 | 3GB+ | Apache-2.0 | ✅ 强中文克隆 |
| GPT-SoVITS | 2GB+ | MIT（社区） | ✅ 少样本微调 |

都需要 GPU（6GB 勉强）、需要从视频里先分离出人声（ffmpeg + 人声分离），
而且**克隆质量取决于参考音频的干净程度**。

### 为什么我不能直接做

项目规范与 `SECURITY.md` 都写死了：**不模仿未经许可的真人声音**。
一段网上的视频里的人是真人，声音属于他本人；没有他的授权，克隆即侵权。

### 我能做的（需你确认口径）

1. **只允许克隆你本人的声音**（你录一段授权声明 + 提供音频），或
2. **只允许克隆明确标注可商用/可二创的音色**（如 VOICEVOX 角色，带署名要求），或
3. 你提供**书面授权**（例如你自己拍的视频里的自己）。

确认后我按"授权登记 → 音色入库 → 带 consent 记录调用"的方式实现，且每条音色都记来源。

## 2. 「从免费二次元音色库获取音色」

| 来源 | 许可 | 代价 |
|---|---|---|
| **VOICEVOX**（ずんだもん 等） | 引擎 LGPL-3.0；**每个角色有单独使用条款**，多数要求署名、禁止商用 | 引擎约 1GB + 常驻进程 |
| A.I.VOICE / CoeFont | 商业授权 | 需付费 |
| HuggingFace 社区音色 | 各自不同 | 质量参差 |

**推荐 VOICEVOX**：免费、音色多、条款清晰。接入方式与 Kokoro 一致（独立侧车 + HTTP），
但必须把每个角色的**署名与使用限制写进素材库索引**，并在发送时保留署名。

需要你确认：是否接受"每用一次某个角色音色，回复里带一次署名"这种形式。

## 3. 「发视频让它像视频里一样唱」

可行路径（不改现有架构）：

```text
视频 → ffmpeg 抽帧(3-6 张) + 抽音轨
     → 视觉理解（现有 VisionProvider）：画面/风格/情绪
     → ASR（现有 SenseVoice）：人声里的歌词/语言
     → 汇总成"音乐意图"（风格 / BPM / 语言 / 情绪 / 参考旋律描述）
     → ACE-Step：reference_audio 做风格参考 + 原创歌词
     → 成品 MP3 → QQ
```

**能做的**：模仿风格、情绪、节奏、语言。
**做不到的**：复刻视频里那个人的嗓音（同 §1 的授权问题），以及精确复刻旋律（版权）。

这条我建议排在"音色方案"之后做，因为它复用同一批组件。

## 7. 部署前置：VOICEVOX 引擎

1. 下载 VOICEVOX 引擎（官方 GitHub Releases，**需要能访问 GitHub 的网络**）；
2. 解压到 **D 盘**（例如 `D:\...\runtime\voicevox`），运行 `run.exe`，默认监听 `127.0.0.1:50021`；
3. PAA 侧把 `PAA_MEDIA_TTS_PROVIDER` 改成 `voicevox`，可选 `PAA_MEDIA_VOICEVOX_URL` / `PAA_MEDIA_VOICEVOX_SPEAKER`。

**署名**：VOICEVOX 多数角色条款要求标注角色名。适配器已在 `VoicevoxVoice.credit` 里保留角色名，
需要时在回复末尾追加一次署名；如果所用角色条款不要求，可以不显示。

## 9. ACE-Step LM：定位到「组合加载」才崩

| 实验 | 结果 |
|---|---|
| LM 单独初始化（cuda / cpu，backend=pt） | ✅ 成功，28 秒 |
| LM 单独初始化，dtype=bf16 on CPU | ✅ 成功 |
| **已加载 DiT 后再初始化 LM** | ❌ 访问违例 `0xC0000005`（bf16、CPU、GPU 都试过） |

结论：不是 LM 本身坏，而是**同一个进程里 DiT（int8，约 4.8GB 显存/CPU 副本）与 1.7B LM 共存**时崩。
这与显存和内存都有关，属于"进程内顺序"问题，不是配置能解决的。

**下一步方案**（推荐）：不再自己拼 handler，改用 ACE-Step 官方 API 服务（它自己管理模型生命周期与卸载），
PAA 只当 HTTP 客户端。这样唱歌的"人声"能力由上游负责，我们只负责调度与发送。
## 10. 唱歌人声的真正根因：页面文件（commit）不够，不是显存

2026-10-26 01:40，把设备组合穷举后拿到决定性错误：

```
OSError: 页面文件太小，无法完成操作。 (os error 1455)
```

**实测数据**：

| 指标 | 值 |
|---|---|
| 物理内存 | 15.3 GB |
| 提交上限 | 26.8 GB（= 15.3 内存 + 11.7 页面文件） |
| 页面文件峰值 | **5320 MB**（平时 159MB） |
| ACE-Step LM 模式所需 | DiT + LM(1.7B fp32 约 6.8GB) + text encoder + VAE 同时驻留，**超过 26.8GB** |

这同时解释了之前两件"怪事"：

1. `0xC0000005` 访问违例 —— 提交内存耗尽时的原生崩溃；
2. PostgreSQL 卡进恢复模式 —— 同一时刻提交耗尽，PG 被系统杀掉。

**设备组合穷举结果**（30 秒、int8 DiT）：

| 组合 | 结果 |
|---|---|
| DiT GPU + LM GPU + VAE GPU | ❌ 0.12GB 空闲显存，VAE 解码崩溃 |
| DiT GPU + LM CPU + VAE CPU | ❌ LM 阶段正常（能生成含人声描述的 caption），解码后 os error 1455 |
| DiT GPU + LM CPU + VAE CPU + batch=1 + 15s | ❌ 同上，提交内存仍然不够 |
| 全 CPU | ❌ 立即 os error 1455 |

**结论**：6GB 显存不是天花板，**提交内存才是**。把页面文件扩到 C 8GB + D 32GB（合计约 40GB）后，
同一套 LM 组合应当能跑完；脚本已改为这个配置。
